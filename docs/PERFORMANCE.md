# demo.4 性能测量记录

本记录用于解释本轮优化的测量方法与实际边界。2026-09-13 已完成 demo.3 基线，以及完整干净源码回归、最终美术调整后的 demo.4 性能测量。最终测量期间源码未变化，也没有页面异常。以下是特定测试环境中的结果，不是跨硬件性能认证。

## 测量方法

使用 `tools/profile-rendering.js` 在同一台 Windows 开发机、同一 Chromium / SwiftShader 后端中串行测量。每轮只有一个浏览器和一个页面，结束后关闭浏览器及本轮启动的临时本地服务。

- 窗口为 **1366 × 768**，设备像素比为 **1**。
- 基线对应 demo.3；最终结果对应 demo.4 的完整建筑模型、11 个环境绘制对象和核心渲染合批版本。
- 这是包含模型、场景和相机构图变化的整合比较，不是把每项优化分别开关的隔离实验。
- 两轮均使用 `?test=1`。该入口为截图验证保留绘图缓冲区，普通玩家入口不保留；因此这些数字不能直接充当普通玩家入口的绝对帧率。
- 早期场景使用“海港新生活”的 5 栋建筑开局。
- 密集场景为固定 **165 栋建筑**、贯通道路、约 1,000 名居民的合成负载存档，用于压力比较，不是正常经济通关路径。
- 每个场景依次测省电和标准档，预热 1 秒、采样约 3.2 秒。表格统一比较相同的**标准档 30 帧目标**；标准档在 DPR 1 设备上仍以 DPR 1 绘制。
- 绘制调用、三角形和几何资源数来自 `renderer.info`；帧率来自实际提交帧数 / 经过时间。帧回调耗时只统计真正提交绘制的回调，不把为等待显示刷新而提前唤醒的空回调算作一帧。
- 页面主线程耗时来自 Chrome DevTools Protocol 的 `Performance.getMetrics().TaskDuration` 差值，包括脚本、样式和布局等页面主线程工作；**不包含全部 GPU / 软件光栅进程，不是整机 CPU 百分比**。
- 堆内存为 CDP `JSHeapUsedSize` 的采样末值，未强制垃圾回收，不代表峰值或整个浏览器的内存。

默认 ANGLE 后端在基线启动时即丢失 WebGL 上下文，所以同后端比较显式使用 `--software`。**交付游戏没有被强制切换到软件渲染。** 默认硬件后端、不同显卡和长时间人工游玩的性能仍需单独确认。

## 最终结果：标准档

| 场景 / 指标 | demo.3 基线 | demo.4 最终 |
| --- | ---: | ---: |
| 早期：实际帧率 | 9.98 fps | 29.85 fps |
| 早期：绘制调用 | 178 | 21 |
| 早期：三角形 | 39,492 | 15,462 |
| 早期：帧回调中位耗时 | 1.4 ms | 0.4 ms |
| 早期：页面主线程耗时 / 秒 | 73.01 ms | 46.33 ms |
| 密集：实际帧率 | 8.70 fps | 19.12 fps |
| 密集：绘制调用 | 2,453 | 185 |
| 密集：三角形 | 160,342 | 65,632 |
| 密集：帧回调中位耗时 | 22.9 ms | 1.1 ms |
| 密集：帧回调 P95 耗时 | 53.8 ms | 1.9 ms |
| 密集：页面主线程耗时 / 秒 | 225.24 ms | 60.44 ms |
| 密集：渲染器几何资源数 | 1,304 | 60 |
| 密集：JS 堆末值 | 30.36 MiB | 11.08 MiB |

密集场景的绘制调用下降约 **92.5%**。页面主线程提交工作也明显减少，但同一软件后端下的密集场景仍未达到 30 fps；不能把“30 帧目标”写成“实测稳定 30 帧”。最终标准档密集采样仍出现一次 116 ms 的长任务，短时间中位数改善不能替代对最差交互和周结算延迟的关注。

暖缓存下连续 5 次密集城镇统计重算，最终版本为 **3.8–4.8 ms**，基线为 **10.1–44.9 ms**。这组单独重算在暂停后执行，不能与正在绘制、可能受软件图形线程争用影响的周结算耗时混用。

可随源码审计的记录：[默认后端失败记录](benchmarks/baseline-default.json)、[同后端基线](benchmarks/baseline-software.json)、[最终测量](benchmarks/final-software.json)。记录包含采样指标、渲染后端和源码来源，没有本机用户目录或凭据。

最终报告的源码 SHA-256 在测量开始时直接采集，结束后再次核对。基线当时没有采集工作区字节哈希和自动变更检测，这两个字段明确记为未知（`null`）。另附可独立核验的已验收 demo.3 本地归档及其源码哈希作为参考，不能将归档哈希当作测量时工作区哈希。基线只在测试状态接口增加三角形计数的诊断补丁，没有改变渲染或模拟行为。

完整本地记录位于 `dist/performance/`；最终截图为 `final-harbor.png`、`final-dense.png`。第一轮中间结果 `after-software.json` 保留用于追溯，不混入本表。`dist/` 是本地验证产物，不进入源码提交。

## 已实现的控制

- 新玩家默认标准 **30 帧**；已有合法省电 / 标准 / 流畅偏好在读取存档或开启另一段故事时保留。
- 帧调度保存下一帧截止时间，并提前注册 `requestAnimationFrame`，避免先等完整帧间隔、再额外等一次显示刷新。
- 暂停时通常降至 **10 帧**；拖动、缩放和建造预览会短暂按所选档响应，再退回低频。阻塞菜单为 **1 帧**；隐藏页面取消计时器与帧请求，停止绘制、模拟和音频。
- 道路主体 / 标线、拥堵提示、交通移动体和热力图使用实例批量绘制。密集城镇开启服务图层不再额外产生 324 次独立绘制。
- 建筑使用共享的完整顶点色模型，停止为不可见旧建筑分配原有模型。静态建筑完成出现动画后不再持续晃动或重算局部矩阵。
- 鼠标先用地面射线定位，再最多检查附近 7 × 7 格中的建筑屋顶，既避免遍历全部 324 个地块实例，也能正确选中屋顶，防止误建或误拆；悬浮状态按输入或城镇变化更新。
- 统计重算在单次调用内缓存建筑索引和最近道路查询。这项缓存本身不改变原有经济公式、寻路选择及存档数据语义；新增街区玩法的收入另按对应规则计算。
- 地图范围、移动体上限 60、路径缓存上限 2,048、效果上限 96 保持有界；重复重建继续释放旧图形资源。

受控 60 Hz 显示时钟、每次绘制占用 3 ms 的纯 Node 调度复核得到：标准档间隔 33.33 ms、流畅档 16.67 ms、省电档在 50 / 33.33 ms 间交替达到平均 24 帧、暂停档 100 ms；隐藏后新增 0 帧且没有待处理计时器。此项只验证调度逻辑，不代替实际浏览器测量。

## 验证与复现

性能专项 5 项已经通过，覆盖画面偏好迁移、帧率上限与隐藏停止、反复重建资源边界、密集图层提交上限，以及普通入口的设置保留和后台音频行为。随后完整干净源码回归通过，再执行本次最终美术采样。完整回归数量及实际发行包验收统一见[试玩发布说明](DEMO_RELEASE_NOTES.md)，不以性能探针代替功能和发行验证。

在已安装开发依赖与 Playwright Chromium、配置好 Python 的开发环境中运行：

```powershell
node tools/profile-rendering.js --label=hardware-check
node tools/profile-rendering.js --software --label=final
```

`--software` 仅在明确需要软件后端时使用。可通过 `SUNNY_TOWN_PYTHON` 指定 Python 解释器，通过 `SUNNY_TOWN_PROFILE_URL` 指定本地服务地址；默认使用 `http://127.0.0.1:8767`。脚本会记录后端、源文件哈希和测量期间源码是否变化。结果、截图写入 `dist/performance/`，源码变化或图形上下文失效时不得将该轮结果用于比较。

性能验证与其他浏览器回归应串行运行，避免测试进程互相争用 CPU，也避免给玩家机器增加不必要的负担。
